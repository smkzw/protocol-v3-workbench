结论：**不是"削弱了不变量"，而是"把不变量从 fail-closed 改成 fail-quiet"** —— 数据仍干净，但"AI 曾试图代答"这一审计信号从"整轮失败（响亮）"退化为"一段小字（安静）"。在监管写作产品里，这个信号本身就是质量数据，不能只留在自由文本里。

#### 3.1.2 新引入的语义反转通道（决定性发现）

`_normalize_enum_value`（`:247-264`）用"别名/枚举 token 作为子串出现即命中"的 contains-match 做兜底。**在真实别名表上实测**（直接调用仓库函数）：

| 字段 | AI 原始表述 | 归一化结果 | 判定 |
|---|---|---|---|
| `immunogenicity_relevance` | `not expected` | `expected` | **语义反转**（正是 F-A 触发的字段） |
| `immunogenicity_relevance` | `unexpected immunogenicity` | `expected` | **语义反转** |
| `immunogenicity_relevance` | `no potential for immunogenicity` | `potential` | **语义反转** |
| `immunogenicity_relevance` | `无潜在风险` | `potential` | **语义反转** |
| `exposure_scope` | `non-systemic / local` | `systemic` | **语义反转** |
| `exposure_scope` | `主要局部，非全身` | `systemic` | **语义反转** |
| `device_dependency` | `无一体化装置` | `integrated` | **语义反转** |
| `technology_type` | `非小分子（单克隆抗体）` | `monoclonal_antibody` | 反转（结果碰巧可接受） |
| `study_phase` | `非II期，为III期` | `III期` | 命中最后一个 token，侥幸正确 |

两条附加事实：

1. **该分支不强制 `fact_kind` 回退**。命中后走 `if value not in FIELD_ENUM_VALUES[...]` 为假 → 不加降级注、不改 kind。于是 AI 标 `source_extracted`（带 source_id）或 `user_stated` 的**反转值**会被原样记录，且新测试 `test_enum_value_containing_alias_still_normalizes` 正是把这个行为**锁定成期望**（断言 `value == "expected"` 且 `fact_kind == USER_STATED`）。修复前这类输入会 raise（整轮失败，用户看得见），修复后会静默写成事实——**这是本 commit 唯一真正的"削弱"**。
2. **"最长匹配"规则本身不自洽**：比较的是 `len(alias) > len(best)`，而 `best` 存的是**目标 token**。故 `不依赖外部装置` → 命中 `不依赖`(3) 得 `none`(4 字符)，再命中 `外部装置`(4) 时 `4 > len("none")=4` 为假 → 保留 `none`（本审阅实测输出 `none`）。即结果取决于目标 token 的字符长度，而非别名长度，不是它自称的 longest-match。
3. **docstring 两个示例都是假的**：`"预期无关"` 实测**不**命中（`预计无关` 才是别名键，二者不同字）；`"unlikely / low risk"` 不含子串 `expected`。说明该函数从未按其自述示例验证过。

#### 3.1.3 F-A 未覆盖的同类 raise（R14 断点家族）

`_validate_ai_response` 内仍有 15 处 `raise ValueError`，其中**逐提案级**且会因模型固定措辞而确定性复发的至少有：

### 3.2 F-B：谱系歧义改"取最新迁移" + 未知错误码改走 fresh planner

#### 3.2.1 是否会掩盖真正的数据冲突 —— 结论：源冲突不可能，但选择时机/留痕/审计三处有缺陷

**不冲突的部分（守卫充分，应予确认）**：`_contract_plans_with`（`:2728-2780`）已按 `artifact_id + extraction_revision + document_sha256 + planner_prompt_version + planner_contract_fingerprint + status=active` 过滤；`_build_contract_migration_plan`（`:2783-2907`）再校验 `planner_contract_fingerprint` 与 `planner_input_hash == 当前输入哈希`，并用**当前**源 span 重新 canonicalize 章节。因此"取到另一份源快照的计划"被硬拦，不会发生。

**缺陷 1｜选择发生在校验之前**：先 `sort(created_at, plan_id)` 取最新（`:2300-2318`），再对**这一份**做 `_build_contract_migration_plan`。若最新那份恰好 `planner_input_hash` 不匹配或 `document_role` 不在白名单，会抛 `document_plan_contract_source_input_hash_mismatch` / `..._not_allowlisted`，**整轮重试硬失败**——尽管旁边可能躺着一份完全合格的老计划。正确做法是"按新→旧顺序，取第一个通过全部校验的候选"。

**缺陷 2｜被丢弃的候选不留痕**：只写 `logger.warning`（stderr），谱系字典（`:2355-2385`）只记录被选中计划的 `source_plan_id`。**持久层与审计事件里看不出"曾存在 2 份计划、丢弃了哪一份、依据什么规则"**。对监管写作产品，这是审计可重建性的缺口。建议在谱系/重试事件里加 `document_plan_contract_candidate_source_plan_ids: [...]` 与 `..._selection_rule: "latest_validated"`。

**缺陷 3｜同批混结构风险**：同一 artifact 的其它 item 若已按另一份计划生成成功，本次重试的 item 迁移到最新计划后，一个 batch 内会同时存在两套章节结构（chapter_id/order 不一致），下游装配与后续引用可能错位。至少应在批次上打"结构谱系不一致，需人工复核"标记。

## 4. F-C 产品级最小修复方案（意见书，不含代码改动）

### 4.1 事实重述与既有能力盘点

- 现状：框架写入被 `authoring_writes_blocked_by_pipeline(stage)` 拦截（`medical_writing_research_pipeline.py:76-93`），`triaging` 不在放行集合内，故 `完成第一步` 的影响确认返回 409，文案为 `研究流水线当前处于 triaging；…请等待当前节点结束或先处理页面显示的用户等待项。`（`:95-105`）。
- **产品已有但未被使用的能力**（这是"最小修复"的依据）：
  - 终态集合已存在：`TERMINAL_STAGES = {corpus_ready, round2_ready, failed, cancelled}`，且终态与四个"用户动作等待阶段"**本就允许写入**（`:62-80`）；
  - 取消能力已存在：`cancel()` 置 `cancelled`（`:758-764`），HTTP 端点 `/api/projects/{project_id}/medical-writing/research-pipeline/cancel`（`main.py:8232`）**已在前端接线**（`MedicalWritingAuthoringJourneySetup.jsx:922`），取消按钮在非终态即渲染（`:2993-3005`，title="取消当前研究流水线（已完成步骤会保留审计）"）；
  - 进度能力已存在：`STAGE_PROGRESS_RANGES`（searching 8-22 / triaging 22-35 / preparing 50-58 / translating 68-85 / analyzing_round1 85-90 / analyzing_round2 96-99），前端已有 `research-pipeline-banner` 进度条与 `子步骤 n/N`（`:2799-2830`）。
- 因此 F-C 不是"缺少等待态机制"，而是**三处产品缺陷**：①允许点击后才拒绝（fail-late）；②拒绝处不给出路（cancel 藏在流水线横幅，且按钮语义与"解除冻结"无关联，用户不会想到它）；③长窗口（本地分诊 40-103 min）内用户无"可离开"的承诺。

### 4.2 目标状态机（在既有 stage 上做呈现层定义，不新增后端状态）

| 状态 | 进入条件 | 允许的框架写入 | 用户可见 |
|---|---|---|---|
| `EDITABLE` | stage 为空 或 ∈ 终态 或 ∈ 用户动作等待阶段 | 是 | 正常"完成第一步" |
| `WAITING_BLOCKED` | stage ∉ 终态 且 ∉ 用户动作等待阶段（含 `triaging`） | 否（提交入口前置禁用） | 真等待态（§4.3） |
| `QUEUED` | 用户在 `WAITING_BLOCKED` 选择"等待后提交" | 变更以草稿形式暂存，不写入 | "已排队，分诊结束后自动核验并提交"+可撤销 |
| `RESOLVED` | stage 变终态 | 是 | 队列项自动重开影响面板（见 §4.4 的失败分支规则） |

### 4.3 真等待态的呈现要素（必须同时满足）

1. **前置禁用而非事后报错**：处于 `WAITING_BLOCKED` 时，"确认变更并重新核验"按钮 `disabled`，`title` 给出：当前阶段中文名（检索/竞品分诊/原文准备/翻译/第一轮分析/第二轮分析）+ 进度百分比 + 子步骤 `n/N` + 已用时 + 预期剩余区间（可用 STAGE_PROGRESS_RANGES 与批次均耗时估算）+ 两条出路。
2. **进度可见且自动刷新**：沿用既有横幅（stage 标签 + 百分比 + `n/N`），在影响面板内**同时**给一行紧凑状态（用户此刻的注意力在面板上，不在横幅上）。
3. **可离开承诺**：明确"可离开页面/关闭浏览器：任务在后台继续，服务重启后可自动恢复"——R13 已实测 durable 冷恢复（4 个在途分诊 job 被新 worker 拾起、进度无损），这句话有事实支撑，且直接消解"40 分钟必须盯着页面"的焦虑。
4. **两条出路各一个按钮**（见 §4.5），且都不需要用户理解 `triaging` 这个内部词。
5. **无死路文案**：删除"请等待当前节点结束或先处理页面显示的用户等待项"里的后半句（此刻并不存在"用户等待项"，会误导用户去找不存在的东西）。

### 4.4 解除条件（必须显式、可观测、可测）

| 触发 | 解除动作 |
|---|---|
| stage → `corpus_ready` / `round2_ready`（成功终态） | 解冻；`QUEUED` 项**自动重开影响面板**并用**新快照**重算影响，需用户再点一次"确认变更并重新核验"（不静默写入） |
| stage → `failed`（含分诊 partial_failed 投影为 failed 的情形） | 解冻**并**在面板内提示"竞品检索/分诊未完成：提交后将重新检索"；`QUEUED` 项**不自动提交**，改为高亮"现在提交（将重新检索）" |
| stage → `cancelled`（用户点取消，或系统取消） | 立即解冻；`QUEUED` 项自动重开面板（快照已作废，影响需重算） |
| stage ∈ 用户动作等待阶段（awaiting_*） | 本就允许写入，按现状直接提交 |
| 用户点"取消分诊并提交变更" | 先调用既有 cancel 端点（stage→`cancelled`）→ 解冻 → 提交变更 → 提示"已取消本次检索/分诊，提交后系统将重新检索" |
| 页面刷新/会话恢复 | 从持久态重建：若 stage 已终态而存在 `QUEUED` 项，重开面板（队列状态需持久化，或退化为"刷新后需重新提交"并明说） |

### 4.5 两条出路的具体设计

**出路 A（推荐默认）｜"等待分诊完成后提交"**
- 一次点击把当前影响面板结论与待提交变更暂存（前端 state 或既有草稿机制），进入 `QUEUED`；按钮变"已排队 · 可撤销"。
- 好处：保住分诊快照（符合冻结设计意图），用户零损失；代价：等待 40-100 分钟。
- 边界：若用户离开页面且队列无法持久化，则必须在进入队列时明确写"刷新页面后需重新提交"。

**出路 B｜"取消分诊并提交变更"**
- 二次确认，文案必须写明后果："已完成的检索/分诊结果将作废，提交后将按新框架重新检索（预计再次耗时 X 分钟）"，并给"取消"。
- 复用既有端点与既有 `cancelled` 终态，**无新增后端概念**。
- 好处：给用户真正的决定权，冻结不再是死墙；代价：重跑检索。

**出路 C（可选，成本略高）｜让分诊可暂停/可重排**
- 仅当 A/B 仍不能满足现场需求时再做；不在本轮最小方案内。

### 4.6 根因削减（仍属产品级，优先级低于 A/B）

当前流水线在**进入写作工作区时自动 start**（前端 `:1391-1405` 在"start 从未到达"时主动补发），而此刻第一步通常尚未提交——冻结窗口与编辑窗口天然重叠，F-C 因此必然发生。最小削减：**把自动 start 推迟到第一步提交成功之后**（或让自动启动的快照显式标记为"临时快照，框架变更即作废"）。这样"编辑框架"与"分诊在途"不再互相排斥，F-C 整类消失，且不需要用户理解任何新概念。

### 4.7 验收标准（R14 可直接照此验证）

1. stage=`triaging` 时进入影响面板：确认按钮为禁用态且 `title` 含阶段中文名、进度、`n/N`、两条出路；**不产生 409**。
2. 点"等待后提交"→ 出现"已排队"状态；分诊进入终态后**自动重开**影响面板，且未静默写入框架。
3. 点"取消分诊并提交变更"→ 二次确认 → 取消成功（stage=`cancelled`）→ 框架提交成功 → 检索重新开始；全程无英文/内部词。
4. 分诊在途时刷新页面：等待态与队列状态一致呈现（或明确提示需重新提交）。
5. 文案检查：用户可见文本不含 `triaging`、`awaiting_*`、stage 英文名。
6. 明确**不做**：不要求分诊可暂停；不要求缩短本地模型分诊时长（另立性能议题）；不改变终态集合语义。

## 5. F-D 重派 prompt 改进条款（可直接粘贴进 R14 prompt）

### 5.1 现有条款为何失效

R13 已写"AI 步骤可能需要 10-40 分钟……禁止因等待而提前结束测试会话"，但 grok/cursor 会话仍以 `EXIT=0` + 状态叙述收尾（"10 分钟轮询已在后台跑，页面保持打开"）。原因是**机制冲突**：会话要等墙钟时间就必须让出回合，而"提前结束测试会话"与"结束本回合"在 prompt 里没有区分，模型只能二选一；一旦输出 `EXIT=0`，调度侧即视为完成。此外 R13 现场把续作提示写进了 log 文件（模型看不到），说明续作信息的**载体**也要写进条款。

### 5.2 条款草案

```
## 等待与终止纪律（R14 强化版）

T1｜终止 token 唯一性：EXIT=OK / EXIT=BLOCKED 只允许在最终报告的最后一行出现一次。
   任何流水线步骤在途（分诊/事实拆解/语料/翻译/初稿/采纳）时，禁止输出 EXIT 行。

T2｜等待必须发生在回合内：需要等待时用 bash 睡眠后轮询（例：sleep 120，再取一次快照），
   不要把"等 10 分钟"写成回合结束理由。若平台强制让出回合，输出且仅输出一行等待标记：
   WAITING=<步骤名> elapsed=<mm:ss> progress=<n/N 或 %> next=<下一步动作>
   该行不是终止信号；恢复后从该标记继续。

T3｜分档等待预算（超预算才可判"未完成"，且必须写明是预算超时而非死路）：
   竞品分诊 ≤120 分钟（实测 19-25 批约 40-103 分钟）；事实拆解单轮 ≤10 分钟；
   语料准备/翻译 ≤20 分钟；初稿批次 ≤45 分钟；导出/采纳 ≤10 分钟。
   判"停滞"需满足：连续 3 次轮询（间隔 ≥2 分钟）进度计数完全不变，且 UI 无终态文案。

T4｜轮询证据表：每次轮询记一行 (时间戳, 阶段文案原文, 进度 n/N 或 %, 截图文件名)。
   进度在推进时禁止重复点击任何按钮；只有进度停滞才允许用界面重试控件重试一次。

T5｜禁止提前收尾措辞：报告不得以"页面保持打开/轮询已在后台跑/稍后继续"结束；
   未走完链路又未超预算时，只能以 WAITING 行结束本回合。

T6｜续作（重派）prompt 必须自带状态块，且必须写进 prompt 本身（不得只写在 log 文件）：
   PROJECT=<项目名/编号/id>  LAST_DONE=<最后完成的步骤>  IN_FLIGHT=<在途任务与其进度>
   SCREENSHOT_DIR=<路径>  NEXT=<唯一的下一个动作>  KNOWN_LIMITS=<上轮未覆盖项>
   续作会话开局先复核该状态块与页面现状是否一致，不一致以页面为准并记录差异。

T7｜禁止用新项目规避在途任务：若已存在同场景项目，必须在其中继续；仅在项目确实不可恢复
   （页面给出终态失败且无重试入口）时才新建，并说明依据。

T8｜PASSED 不得跨会话继承：上轮观察到但本轮未复验的项，记
   PASSED(上轮观察，本轮未复验)，不得直接写 PASSED。

T9｜环境事件不占用重试预算：版本门/端口占用等环境阻断，记录指纹原文后最多等待 15 分钟
   并每 3 分钟复检一次；仍未恢复则按 EXIT=BLOCKED 收尾，并在报告中标注 P0-ENV。
```

### 5.3 附带建议

- 给 grok/cursor 会话单独设"等待观察员"：由调度侧在 `WAITING=` 行出现后自动重派（间隔 10 分钟），而不是依赖会话自身坚持。R13 已证明重派可用（REDISPATCH/REDISPATCH2 生效），把重派触发条件从"人工判断"改成"WAITING 行 + 计时"即可。
- 派发时把"已知缺陷清单（L6 台账）"一并给出，减少重复上报与重复定级。
