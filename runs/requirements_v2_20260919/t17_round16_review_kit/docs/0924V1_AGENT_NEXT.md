审阅基线为 `455b37ee4530628736bd6b37b622796f13e9498f`。实施前读取当前HEAD；如已有新提交，先将本轮发现映射到新实现，不把旧代码补丁硬套上去。

保持用户已确认需求：摘要预填与从零推荐两入口汇合；关键设计确认后允许有明确非关键缺口的完整结构工作稿；自由编辑先保存，科学差异显式核对；摘要和SOA由AI初生，用户可编辑或要求AI局部修订；当前Office快照为继续编辑和下载来源。公司SOP按已有项目级适用性规则复用，旧方案参数不能自动成为本项目事实。

不得改为全量必填、统一强制上传、把未知当不适用、把同一研究内容让用户抄写多次、以临时案例数值或错误改名方式求测试变绿。

## 三、工作包

### WP-A：预约恢复与stale包路径（最高优先级）

文件：`medical_writing_authoring_journey.py`、现有prefill endpoint、`MedicalWritingAuthoringJourneySetup.jsx`。

1. 先用本包的预约反例在真实模块/数据库上复现；注意当前非force已有超时分支，禁止重复造另一套无关联超时器。
2. 建立或复用持久的运行身份、所有者和输入指纹；UI轮询不能成为唯一的回收驱动。
3. 明确区分：queued/running、观察超时、已发送结果未知、确定失败、已完成、取消请求中、已取消。可以映射到既有状态，不要求照抄新枚举。
4. owner存活/租约有效：返回原handle让页面继续跟踪，不进入新模型调用。
5. 确认owner退出或租约失效且没有结果：先CAS标识unknown_outcome；不得把超过15分钟直接认作服务死亡。
6. 结果已落盘：返回原结果；已发送但可能仍在计算：保留旧逻辑身份与状态，按已有恢复策略处理。不能承诺崩溃边界上外部API物理exactly-once。
7. 明确接管时，保存supersedes/attempt_history并用owner token/fencing校验晚到结果；旧owner不得覆盖新owner已激活结果。
8. 处理真正stale推荐时核对依赖指纹：无关进度事件导致journey升版，不应花一整次模型调用重新生成；若输入确有变化，保留已确认值和未采用候选，更新受影响部分。禁止直接篡改旧package.journey_revision冒充绑定有效。
9. long request不应将全页可保存草稿无限disabled。当前运行继续冻结输入，用户待提交输入有独立可靠缓冲；不是偷偷修改正在执行的任务上下文。

建议复用既有durable job/事件/预约数据库，而不是新建任务框架。若增加lease字段，迁移需向后兼容，旧记录按明确恢复流程读取。

### WP-B：排队变更与取消提交（与WP-A同批集成）

1. 排队意图必须有project_id、操作身份、payload/hash、base revision、状态；优先保存到现有草稿/操作记录。
2. 在队列确认持久化前不得显示“可以离开/已排队”。保留本页模式时如实提示并保护输入。
3. 页面重开恢复原队列；切项目隔离；错误不能直接丢掉payload。
4. 后台结束后重新读取当前journey和impact；需要新的科学确认时展示差异，否则执行原授权，不增加形式性重复确认。
5. `cancelResearchPipeline`返回类型化结果或抛错；取消失败/项目变化直接停止组合操作。
6. 取消accepted但尚非终态则等待原任务终态；取消确认完成后重算impact，不能使用旧preview直接提交。
7. 单击重复、刷新、晚到响应、取消失败、取消成功但研究又变化全部走同一操作记录恢复，不用新UUID伪造成功。

以下是行为合同而非直接复制的现成产品API：

```ts
type CancelOutcome =
  | { kind: 'confirmed_terminal'; pipelineId: string; projectId: string }
  | { kind: 'accepted_pending'; pipelineId: string; projectId: string }
  | { kind: 'failed'; code: string }
  | { kind: 'stale_context' };

// 先检查取消结果和当前项目，再读取新impact。
// accepted_pending绝不等同confirmed_terminal；不复用旧preview_id。
```

### WP-C：翻译规划失败与多父恢复

先抽取一个当前真实失败artifact的完整谱系：项目、文件hash、extraction revision、planner contract、task/source版本、全部失败parent与源错误。228/230可能由极少数文档级规划失败扩散，不能当作228次独立翻译故障盲目重跑。

修复原则：
- 不清空已知父ID来伪装“历史无来源结构错误”。
- 不以lexicographic first作为业务权威source。
- 同文件但不同提取/规划/配置身份的项目分区处理；只有证明相同冻结输入才合并恢复。
- 允许建立既有事件体系中的recovery关系，明确包含所有superseded父运行；不需要覆写旧记录。
- 不把retry_generation=3无条件洗成0；确需新计划应新建明确身份并保留缘由、祖先和预算。
- 修正`document_plan_anchor_filter`等最早根错误；保留后续派生失败与其根的关系。
- 完成针对单文件的真实恢复，再恢复原批未完成项；已经成功的翻译/下载/OCR不重做。

### WP-D：交付末端优先，不再用“已启动”交卷

1. 找到tester2原job：completed则直接读取结果；running继续观察；failed针对根因恢复原job；unknown先核实。不得未经核对再起一份全文任务。
2. 工作稿接收并保存：必须形成版本身份和实际DOCX，而不只是111个目录节点。
3. 打开真实Office，新增唯一文字标记、改一格SOA、改一个页眉/格式，保存、关闭、重新打开并下载。
4. 用Word打开下载版本，验证这些操作真实保留；记录前后文件hash、producer、对象变化，不能只检查文件存在。
5. 真实加入文献、移动引文、删除引文并校对文献表；表格REF和“文献tab存在”不计替代通过。
6. 缺口必须在UI/文档侧可定位：空模板作为正式稿被拒应通过负向测试；有充分正文+非关键缺口应作为工作稿被允许。两项不能合并。
7. 独立完成入口A摘要导入→预填→关键确认→同一稿件链，失败后改走B不得算A通过。
8. 针对多项需手填的既有例子，记录AI已经提供哪些、用户补充哪些，核对是否违反“不重复抄录”。不为达点击目标取消必要科学确认。

### WP-E：有效的测试与交接

- 在一次集中修复和部署后固定窗口；除明确故障注入，不在黑盒测试中更新服务。
- 一个主测试先走完全链；其他测试分别验证恢复、边界和差异研究，不必须四个长全文并发抢同一个本地模型。
- 记录模型服务队列/延迟/资源信号；不根据大并发下的响应慢就判定代码或模型必然不合格。
- `process_exit_code`、`test_run_status`、`business_flow_status`、`artifact_validation_status`分开。EXIT=0只证明进程退出；running就是running。
- 点击日志记录实际鼠标/键盘动作；报告16个业务组不能伪装16次点击。重试和确认不能删掉后再宣布≤20。113次混合交互也不直接等于113次鼠标点击。
- 每项PASS附scenario、build/runtime/model/input身份和真正观察到的动作。声明未运行的下游能力为NOT_RUN。
- 既有Word证据可在相同范围复用；当前R15尚未到达Office，不据此否定历史所有Word能力，也不据历史部分通过外推当前全部链路。
