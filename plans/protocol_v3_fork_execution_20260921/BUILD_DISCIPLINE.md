# 连续构建与测试节奏约束

## 构建节奏与防过度设计（用户2026-09-21追加，覆盖本包旧措辞）
- 当前默认是连续构建，不是“每个F任务都先测试再允许下一个”。F00–F11按依赖完成实现与源码核查；F12统一执行完整产品验收，F13交付。任务实现完成可记implemented，行为证据待统一验收，不虚写verified。
- 不因改了一个文件、一个函数、一个样式或完成一个微步骤而运行测试、build、浏览器回归或发起一次会商；不设逐改测试/TDD红绿循环/阶段全量测试硬门。每个任务附带命令是后续验收目录，绝非即时执行清单。
- 构建中默认只读受影响定义、消费者和diff。只有真实故障阻塞继续实现且源码检查不足以定位，或完整功能批次必须通过最小编译检查才能继续集成时，才运行最小诊断；执行前在现有checkpoint用一句话写出要回答的问题、最小命令与预期信号。已有有效证据直接复用。
- 诊断结束立即回到构建。不新增镜像实现的测试、不为低风险可逆样式修改造测试、不反复全量回归。相同源码、环境和数据没有变化时不重复检查；后续统一验收修复仅重验受影响行为，除非共享合同变化证明需要扩大。
- 完整功能批次是一个可用用户动作闭环，例如“选推荐→确认入事实→生成可用稿”，不是把一个组件的一次小修改命名为批次。能继续完成的依赖任务不能因待最终验收而暂停。
- 新增抽象、适配层、框架、服务、状态仓库、通用引擎、依赖、管理文档前，先说明当前具体缺陷、现有实现为何不足、最小替代方案；没有当下真实消费者或需求证据就不加。优先复用/合并/删除冗余，禁止为假想未来扩展提前搭框架。
- 不把14个任务包变成14套并行状态账本、14次全量测试或14次强制会商。Trellis唯一动态记录，审阅依明确独立判断需要合并安排，worker不要把自己未获授权的额外建议升级为任务。
- 减少过程不能削弱科学准确性、真实用户决定、输入不丢与最终完整验收；验收标准不降，执行时机集中。
