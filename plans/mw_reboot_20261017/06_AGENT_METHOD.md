# Agent 工作方法（取代旧编排）

## 为什么换
旧编排（Codex 总架构 + Kimi/Grok/Hermes/CodeBuddy 执行与会商 + 五人测试者无上限 LOOP + 自检硬门）把大量时间花在调度、等待、记账和环境预检上：一个 loop 目录 225 项，单轮自检 3–6 小时，缺陷账本出现重复计数与口径争议。质量反馈来自角色扮演测试者的主观报告，不可复现。

## 新方法：评测驱动的单主 Agent + 有界工人
| 角色 | 数量 | 职责 | 不做 |
|---|---|---|---|
| 主 Agent（架构/集成） | 1 | 定 schema 与接口、拆工作包、审 diff、跑评测、合入、维护 STATUS/DECISIONS | 不亲自写大块业务代码 |
| 工人 Agent | 1–3 并行 | 在独立 git worktree 完成一个任务合同，带测试 | 不跨合同改文件 |
| 评测 Agent | 1（可与主 Agent 同一会话按需调用） | 只跑 `eval/run.py` 和写报告 | 不改产品代码、不看 held-out 参照正文 |
| 用户 | — | 医学判断：TopK 确认、决定卡合理性抽查、里程碑盲读 | 不做工程验收 |

模型选择：主 Agent 用你最强的编码 Agent；工人可用同一或次强模型。不设会商；只有改动 schema、删除大模块、或医学规则时，请一个不同模型做一次独立 review。

## 单个工作包循环
1. 主 Agent 写任务合同（templates/task_contract.md）：目标、改动范围、DoD、需要的评测/测试。
2. 工人实现：先写失败测试 → 实现 → 单测通过 → 本地跑相关 eval 子集。
3. 主 Agent 审：diff 是否只在范围内；是否引入适应症/药物特定代码（lint）；评测是否不退化。
4. 合入，更新 STATUS.md 一行。
5. 两次尝试无进展 → 换假设或拆小，不重复同一修法。

## 记录（小而够用）
- `STATUS.md`：每个工作包一行（状态、PR、评测分）。
- `DECISIONS.md`：每条决定 3–5 行（决定、原因、被否方案）。
- `eval/reports/`：只存 json + summary.md。截图、日志、浏览器录像放 runtime 目录，不进 git。
- 暂停/交接只需：当前分支、STATUS.md、最新评测报告。

## 测试分层
| 层 | 内容 | 频率 |
|---|---|---|
| 单元 | 渲染器、计算器、检查器、对齐器、状态机 | 每次提交 |
| 合同 | LLM 输出 schema，用录制的响应回放（不调模型） | 每次提交 |
| 质量评测 | eval dev 子集（3 个项目 × 关键章节） | 写作相关 PR |
| 全量评测 | dev + held-out + smoke | 每日/里程碑 |
| 端到端 | Playwright 脚本跑 S0–S5 一条完整路径（录制模型响应 + 一条真实模型路径） | 每日 |
| 人工 | 用户盲读 | 里程碑 |
LLM 扮演"测试者"的浏览器探索只在里程碑做一次，发现的问题必须转成可复现的脚本或评测用例才算立案。

## 硬性禁止
- 按章节标题/关键词/章号决定医学内容。
- 在提示词或代码里加入具体药物、疾病、量表、项目编号相关的分支或句子（lint 拦截）。
- 用正则改写模型正文中的数字或医学内容。
- 修改评测参照或指标来"通过"。
- 把真实方案、IB、竞品下载件、公司文件名放进公开仓库。
- 触碰 live 8910 / 医学监查子系统。

## 保留的通用纪律
先读后改、最小改动、先红后绿、不覆盖他人改动、不做破坏性 git 操作、外部事实要可查证。
